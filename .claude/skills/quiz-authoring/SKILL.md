# クイズ作成スキル（study_archive_hp）

## なぜこのスキルがあるか

このサイトのクイズは**医療者向けの教育コンテンツ**であり、誤った医学的内容を公開すると
実務判断に影響しうる。だから品質は「もっともらしさ」ではなく**素材への忠実性**と
**人間レビューの通過**で担保する。AI は下書きと検証を担い、公開可否は常に管理者（めいき）が決める。

過去の実事故から学んだ規約（理由ごと覚えること）:
- **正答位置の偏り**: 初期78問中73問で正答が先頭選択肢「a」だった。UI に決定論的シャッフルは
  入っているが、データ上も正答位置を分散させる（シャッフル無効環境やデータ流用に備える）。
- **未レビュー公開の防止**: reviewStatus のゲートを飛ばすと未検証の医学的内容が即公開される。
  ファイル単位・設問単位の draft は quiz:build が自動除外するので、**必ず draft で書き始める**。

## データ契約（この形以外を発明しない）

ファイル: `content/quizzes/archive-<YYYYMMDD>-<id>.json`（アーカイブと1対1、`archiveId` が対応キー）

```jsonc
{
  "archiveId": "archive-20260318-1yp7m9p",
  "passThreshold": 0.7,
  "questions": [
    { // 単一選択（type 省略時のデフォルト）
      "id": "q1",
      "prompt": "…はどれですか。",
      "choices": [{"id": "a", "text": "…"}, {"id": "b", "text": "…"}, {"id": "c", "text": "…"}],
      "answerId": "b",
      "explanation": "正答の根拠。素材のどの記述に基づくかが分かる書き方にする。"
    },
    { // 複数選択（完全一致採点・部分点なし）
      "id": "m1",
      "type": "multiple",
      "prompt": "…に該当するものをすべて選んでください。",
      "choices": [{"id": "a", "text": "…"}, {"id": "b", "text": "…"}, {"id": "c", "text": "…"}, {"id": "d", "text": "…"}],
      "answerIds": ["a", "c"],
      "explanation": "…",
      "reviewStatus": "draft"
    }
  ],
  "reviewStatus": "reviewed",
  "generatedBy": "ai",
  "updatedAt": "YYYY-MM-DD"
}
```

- `answerIds` は要素数 2〜(選択肢数-1)、全要素が choices に実在すること。
- 新規設問は**設問単位の `"reviewStatus": "draft"`** を付ける（ファイルが reviewed でも
  draft 設問はビルドから除外される安全弁）。新規ファイルならファイル単位を draft に。
- 既存の reviewed 設問（文言・選択肢・順序）は変更しない。変更が必要なら別途めいきに提起する。

## 作問の品質基準（クオリティの定義）

**素材忠実性が最優先。** 出題材料は `content/quizzes/_sources.json`（title / summary /
overview / keyPoints）。ここに書かれていない医学的内容 — 用量、カットオフ値、禁忌、
固有の薬剤名・検査値 — を推測で補ってはならない。あなたの医学知識が正しくても、
録画で実際に話されたかを確認できない以上、素材外は出題できない。

**素材が薄いなら作らない。** title+summary しか無い回で無理に作ると、素材の言い換え問題
（情報量ゼロ）か知識の創作（規約違反）のどちらかになる。keyPoints が3件以上あり
overview に具体性がある回だけが作問対象。薄い回は「素材不足で見送り」と報告するのが正解で、
それは失敗ではない。（2026-07 時点で24回中18回は detail 未整備の薄い素材。根本対応は
`content/source/lecture-archives.xlsx` に overview/keyPoints を追記して
`scripts/import_archives_from_xlsx.py` で再取込みする作業で、このスキルの範囲外。
必要なら別タスクとして管理者に提起する。）

**良い設問の型:**
- keyPoints の1項目を「現場での判断」に変換する（「まず確認すべきはどれか」「…の目的として
  素材の説明に沿うものはどれか」）
- 素材が抽象的で判断形式に変換すると内容の追加（＝創作）が必要になる場合は、既存コーパスと
  同型のメタ形式（「この勉強会がキーポイントとして挙げているのはどれか」）に留めるのが安全
- 誤答選択肢は素材内・近接領域のもっともらしい概念から作る（明らかなダミーは弁別力ゼロ）
- 解説は「正答がなぜ正しいか」を素材の記述に紐づけて書く（「summaryに…と記載」等）

**避けること:**
- 選択肢の長さ・具体性で正答が透ける（正答だけ詳しい、など）
- 否定形（「誤っているものは」）の乱発 — 使うなら1回あたり1問まで
- 1アーカイブあたり 3〜5問が目安。複数選択は素材に「独立した複数の正しい要点」が
  ある場合のみ 0〜1問（該当するものを**すべて**選ばせる形式にし、prompt に明示する）
- 正答位置の偏り — ファイル内で answerId/answerIds の位置を意識的に分散させる

## 手順

1. **素材確認**: `content/quizzes/_sources.json` の該当アーカイブを読む。新規アーカイブが
   未抽出なら `python3 scripts/generate_quiz_drafts.py` で抽出（複数選択の下書き生成は
   `--multiple`、keyPoints≥3 の回のみ生成される）。スクリプト出力はあくまで叩き台で、
   上記の品質基準で必ず書き直す。
2. **作問**: データ契約どおりに draft で書く。updatedAt は既存設問に触れない追記なら変えない。
3. **検証**: `npm run quiz:build:dry` — バリデーション（answerIds レンジ・choices 実在・
   重複・single/multiple フィールド混用・reviewStatus 値）が全て通り、draft 設問数が
   意図どおり表示されること。
4. **回帰確認**: 公開分に触れていないことを証明する。`shasum public/data/quiz-bank.js` を
   作業前後で比較し不変であること（draft は除外されるので、追記だけなら不変になるはず。
   変わったら何かを壊している）。`public/data/` は絶対に手編集しない。
5. **レビューシート納品**: `docs/quiz-review-sheet-<識別子>.md` を作る。形式は既存の
   `docs/quiz-review-sheet.md` に厳密に合わせる: 冒頭に使い方（判定欄に「OK」または
   「要修正: メモ」→ OK なら reviewStatus を外して `npm run quiz:build`）→ サマリー表
   （ファイル／対象アーカイブ・日付／設問数／状態）→ 設問ごとに設問文・全選択肢
   （正答に ✅）・解説・空欄の判定欄。**転記は一字一句忠実に**（シートと実データの差異は
   レビューの意味を失わせる）。
6. **報告**: 作った設問数／見送った回とその理由／dry-run 結果／回帰ハッシュ一致／
   シートのパス、を簡潔に。公開はしない（めいきの判定後の作業）。
7. **承認後の公開反映**（依頼されたときのみ）: 該当設問の `reviewStatus` を外す（または
   reviewed 化）→ `npm run quiz:build` → dry-run 相当の件数確認 → `npm run build` で
   全体ビルド成功 → 反映件数を報告。

## セルフチェックリスト（完了報告の前に必ず）

- [ ] 全設問が素材（_sources.json）の記述に根拠を持つ（解説から逆引きできる）
- [ ] 新規設問すべてに draft ゲートが効いている（dry-run の draft 件数で確認）
- [ ] `npm run quiz:build:dry` 合格
- [ ] `shasum public/data/quiz-bank.js` が作業前後で一致（公開反映タスクを除く）
- [ ] レビューシートの転記が実データと完全一致
- [ ] `git status` に意図したファイル以外の変更がない
- [ ] git commit はしていない（司令塔または管理者が扱う）

## 禁止事項

- `public/data/` 配下の手編集（ビルドスクリプト経由のみ）
- レビュー承認前の公開（draft ゲートの除去・reviewed 化）
- 素材にない医学的内容の出題・解説への混入
- 既存 reviewed 設問の改変・削除・並べ替え
