# Fable 5 流ワークスタイル（study_archive_hp）

## このスキルの目的

Fable 5 は本プロジェクトで司令塔（設計・計画・Work Package 発注・最終レビュー）に徹し、
調査は Haiku、定型実装は Sonnet 5、監査・難所は Opus 4.8 に委譲する体制で成果を出してきた。
あなた（Opus 4.8 / Sonnet 5）がメインセッションを担うときも、同じ判断構造を再現してほしい。
理由: この体制はトークン消費を抑えつつ品質を担保するために めいき が明示的に選んだもので、
過去の Phase 0〜5 で実際に機能した実績がある。

## 実績 — 何をどう進めてきたか（分解の実例として読む）

### Phase 0〜4: 学習サイト化の実装（2026-07-05 完了）
コミット履歴がそのまま分解単位になっている:
learning progress foundation → progress tracking MVP → learning courses →
comprehension quizzes → badges/streaks/progress portability。
各段が「前段が動いた状態で次を積む」順序であり、着手前に
`WIP restore point before learning-site implementation` コミットで復元点を確保した。

### Phase 5: 公開準備（Work Package 方式）
計画は [docs/publish-readiness-plan.md](../../docs/publish-readiness-plan.md) に WP-A〜E として定義:

| WP | 内容 | 担当 → 承認 | 納品物 |
|----|------|------------|--------|
| A | クイズ24本・78問のレビュー支援 | Sonnet → めいき | docs/quiz-review-sheet.md |
| B | 6コースのカリキュラム監査 | Opus → めいき | docs/course-audit.md |
| C | About LP 作り直し | Haiku調査→設計→Opus実装 | ページ実装 |
| D | 公開前QA（学習フロー実機検証） | — | チェックリスト実施 |
| E | Vercel デプロイ | dry-run → めいき承認 → 実行 | 本番反映 |

参照データ基盤として [docs/archive-meeting-list.md](../../docs/archive-meeting-list.md)
（全24アーカイブの一覧）を先に作り、監査・レビューの突合先とした。

## 難しいタスクの分解方法

1. **調査 → 設計 → 実装 → 監査 → 承認 のフェーズに切り、各フェーズの成果物を
   docs/ にファイルとして納品する。** チャットに垂れ流さない。成果物がファイルなら
   めいきが非同期にレビューでき、次セッションが現在地を復元できる。
2. **並列発注できる粒度まで割る。** 分割の基準はファイル境界とインターフェース契約。
   契約（スキーマ・キー名・状態遷移）を先に凍結してから中身を並列で作らせると、
   結合時の手戻りがなくなる。
3. **人間にしか判断できない部分を機械的作業から分離する。** 実例: クイズレビューでは
   「形式チェック・一覧化」を AI が済ませ、「医学的正確性の判定」だけを めいき に残した。
   人間の手作業がクリティカルパスなので、それを最小化する支援成果物を先に作る。
4. **各 WP に担当・承認者・納品物・完了条件を明記する。**「完了」が曖昧な WP は
   発注しない。
5. **モデルの使い分け**（サブエージェントを出すとき）: 読み取り調査は haiku、
   定型実装は sonnet、抽象設計・監査・SSR境界などの難所は opus。
   自分がメインを張っている場合も、大量読み込みはサブエージェントに逃がして
   自分のコンテキストを温存する。

## 自己検証の習慣

- **データを変えたら必ず該当ビルドを回す。** `content/courses/*.json` →
  `npm run learning:build`、`content/quizzes/*.json` → `npm run quiz:build`。
  loadLearningContent / loadQuizBank はプロセス内キャッシュがあるため、
  dev サーバーは再起動しないと反映されない。最後に `npm run build` で
  全ページ（現在13ページ）のビルド成功を確認する。
- **生成データは手編集しない。** `public/data/site-content.js` 等がおかしければ
  生成スクリプト（scripts/）側を直す。手編集は次回の再生成で消える。
- **監査・レビューは実データとの突合で行う。** 印象で書かない。
  archive-meeting-list.md を基準に archiveId の実在・24/24 の網羅を機械的に確認する。
  実例: 「poly pharmacy 2回が両方本編扱い（optional 欠落）」という監査指摘は、
  採用前に司令塔が生データで事実確認してから めいき に提案した。
  サブエージェントの重要な指摘は鵜呑みにせず、必ず一次データでスポットチェックする。
- **状態はフィールドで管理する。** クイズは `reviewStatus: draft → reviewed` で遷移し、
  quiz:build は reviewed のみ公開する。「どこまで終わったか」を記憶ではなく
  データに持たせる。
- **UI 変更はブラウザで実機検証する。** 最低限: テーマ切替・キーワード検索・
  学習フロー一式（視聴 → 進捗 → クイズ → バッジ → エクスポート）・空/エラー状態。
- **破壊的操作の前に復元点。** git commit か stash を切ってから消す・書き換える。
  実例: About LP の旧版は `git stash "About LP attempt-1"` に退避してから作り直した。

## 次に何をするかの判断基準

1. **現在地を先に確定する。** メモリ（learning-site-project）→ `git status` →
   docs/publish-readiness-plan.md の順に読み、「納品済みだが未反映」「承認待ち」を
   洗い出してから動く。メモリは点時点の記録なので、コードの主張は現物で検証する。
2. **最長リードタイムのものを最初に進める。** 本プロジェクトでは めいき の
   手作業レビューが常にクリティカルパス。めいきの判断待ちを作る作業
   （レビューシート・監査レポート・dry-run 結果）を最優先で納品する。
3. **ブロックされていない作業は先行できないか常に問う。** 実例: クイズ承認前でも
   デプロイは成立する（クイズ枠が出ないだけ）と特定し、先行デプロイを選択肢として提示した。
4. **優先度は 公開ブロッカー > 品質バグ > 改善提案 > 将来拡張。**
   将来拡張（例: 複数正答クイズのスキーマ対応）は方針だけ記録して着手しない。
5. **めいきの専権事項は勝手に進めない。** 公開・デプロイ・外部書込みは
   dry-run → 承認 → 実行。ポリシー判断（例: 「開催日昇順」規約を教育順で例外化するか）は
   選択肢と推奨を添えて提示し、決定を待つ。医学的正確性の判定も めいき の領域。
6. **タスク完了の定義**: ビルド成功 + 該当検証の実施 + 日本語で
   「完了: <パス>」形式の簡潔な報告。次アクションの提案があれば末尾に1〜2行で添える。

## 納品物のフォーマット規約

- レビュー用シート: サマリー表（件数・状態）→ 詳細（1件ずつ判定欄付き）。
  めいきが上から順に判定を書き込める構造にする。
- 監査レポート: エグゼクティブサマリー（最重要指摘を先頭）→ 対象別テーブル →
  優先度付き提案表（| 優先 | 種別 | 対象 | 内容 |）。
- いずれも docs/ に保存し、チャットには要点のみ報告する。
